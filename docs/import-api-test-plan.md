# KAN-59 업로드 API 준비

2026-09-28: API와 실행 테스트를 추가했다. 아래는 준비 당시 계획이며 현재 선택은 [구현 문서](import-api-implementation.md)를 따른다. 정적 응답 파일은 참고 예시, 실제 API 테스트는 CardImportApiTests다.

기준: 머지된 KAN-54 §6.2·7.1 및 기존 ApiResponse/ApiError 형식. **요청·응답 예시와 검증 계획이며, 컨트롤러·토큰·DB 반영은 아직 구현하지 않았다.** KAN-56~58 리뷰 결과를 반영한 후 실행 가능한 API 테스트로 연결한다.

## 요청

`POST /api/card-expenses/imports`, EDITOR 세션 필요. Content-Type은 multipart/form-data와 boundary를 사용한다. 브라우저에서는 FormData를 보내고 Content-Type을 직접 고정하지 않는다.

| 요소 | 미리보기 | 반영 |
| --- | --- | --- |
| 쿼리 dryRun | 생략 또는 true | false |
| multipart file | .xlsx 파일 1개 | 미리보기와 동일한 파일 바이트 |
| multipart previewToken | 필요 없음 | 미리보기에서 받은 불투명 서명 토큰 |

미리보기는 업무 데이터와 이력을 모두 저장하지 않는다. 파일을 서버에 보관하지 않고 반영 요청에서 다시 받는다. dryRun 생략이 쓰기를 유발하지 않는 것을 반드시 검증한다.

## 성공 응답 예시

`src/test/resources/expense/importing/import-api-examples.json`에 가상 응답 4개를 준비했다. 성공 HTTP 상태는 **200 제안**이며 KAN-54는 이를 명시하지 않았다.

- previewPartial: 8월 READY 추가 2건·동일 1건, 9월 BLOCKED. totals는 READY만 합산하고 오류 월은 기존 내역이 있어도 0건으로 표시한다.
- applyPartial: 같은 예시의 반영 결과. dryRun=false, 새 토큰은 발급하지 않는다. 부분 성공 이력은 PARTIAL이며 성공 응답에 status 필드를 임의로 추가하지 않는다.
- previewAllBlocked: 모든 월에 오류가 있어도 문제를 확인할 수 있는 미리보기 **200 제안**. 실제 반영만 422. 반영 버튼을 비활성화한다.
- previewEmptyReady: 머리글이 유효한 빈 월. 제거 예정 2건을 표시하고 확인 전에는 삭제하지 않는다.

토큰 문자열은 예시용이며 인증·반영에 사용할 수 없다. 반영 응답에서 토큰은 예시상 생략했다. null과 생략 중 어느 형식을 쓸지는 DTO 작성 전에 확정한다. 실제 파일명 대신 sample.xlsx만 사용한다.

## 오류와 화면 동작

오류 본문은 기존 규약처럼 최상위 `code`, 사용자용 `message`, `fieldErrors`를 사용하며 data로 감싸지 않는다. 상태와 코드 중 설계에 확정된 내용과 제안을 아래에서 구분했다.

| 상황 | HTTP | 코드/확정 여부 | 화면 및 검증 |
| --- | --- | --- | --- |
| 세션 없음 | 401 확정 | 기존 인증 코드 재사용 | 로그인 안내, 반영 없음 |
| VIEWER | 403 확정 | 기존 권한 코드 재사용 | 미리보기·반영 모두 차단 |
| file 누락·빈 파일 | 400 제안 | VALIDATION_FAILED/EMPTY_FILE 제안 | 파일 선택 안내 |
| xls/xlsm·손상·읽을 월 없음·중복 월 | 400 확정 | 읽기 계층 코드의 API 매핑 제안 | 파일 수정 요구, 반영 없음 |
| 고정 머리글 오류 | 400 확정 | INVALID_LAYOUT 확정 | 열 위치·머리글 확인 안내 |
| 파일 크기 초과 | 413 확정 | FILE_TOO_LARGE 제안 | 파일 크기 안내 |
| dryRun에 잘못된 값 | 400 제안 | VALIDATION_FAILED 제안 | 자동으로 false로 해석 금지 |
| 토큰 누락·위조 | 400 확정 | PREVIEW_TOKEN_REQUIRED/INVALID 제안 | 새 미리보기 요구 |
| 토큰 만료·파일/DB/파서 버전 변경 | 409 확정 | PREVIEW_STALE 확정 | 새 미리보기로 돌아가기 |
| 모든 월 BLOCKED인 반영 | 422 확정 | NO_APPLICABLE_MONTHS 확정 | 문제 행 수정 요구 |
| 반영 중 예상치 못한 오류 | 500 제안 | 기존 INTERNAL_ERROR | 업무 데이터 롤백, 재확인 안내 |

예시: `{"code":"PREVIEW_STALE","message":"내용이 변경되었거나 미리보기가 만료되었습니다. 다시 미리보기해 주세요.","fieldErrors":{}}`. 문구와 빈 fieldErrors의 표현은 구현 시 기존 ApiError 직렬화와 맞춘다. 토큰·원문 셀·참석자 이름·POI 내부 메시지를 오류 응답이나 로그에 노출하지 않는다.

파일 한도는 KAN-54의 5MB를 기존 읽기 계층이 **5 MiB(5,242,880바이트)**로 구현한 상태다. 동일 값을 적용할지 명시적으로 맞추고, multipart 요청 전체 한도는 boundary·토큰 오버헤드를 수용해야 한다. 프록시와 Spring이 먼저 거부하는 413도 화면에서 처리 가능해야 한다.

## 필수 API 테스트 순서

1. EDITOR가 dryRun을 생략해 올리면 미리보기와 토큰을 받고 모든 테이블이 불변인지 확인한다. true도 동일하게 검증한다.
2. 같은 바이트와 토큰으로 false 반영 시 READY만 저장하고 BLOCKED의 내역·일정·참석자는 모두 보존한다. KAN-58 결과와 응답 건수를 비교한다.
3. READY 빈 월은 미리보기에 삭제 예정 수를 표시하고 실제 반영 후 비활성화한다. 오류로 빈 월은 삭제하지 않는다.
4. WARNING만 있는 월은 READY로 반영한다. 같은 행에 여러 ERROR가 있어도 skippedRows는 행 단위로 한 번만 센다. blockedMonths는 월 수다.
5. 고정 Clock으로 10분 토큰 만료를 검증한다. 경계는 `now >= expiresAt`이면 만료로 하는 것을 제안한다. 파서 버전 변경·다른 파일 바이트·DB 변경은 각각 409다.
6. 파일명만 같고 내용이 다른 경우도 409. 파일명이 달라도 바이트가 같은 경우의 표시/이력 정책은 별도로 확정한다.
7. 미리보기 뒤 다른 업로드가 같은 월을 수정하면 이전 토큰의 반영을 막고 먼저 반영된 데이터를 보존한다. 대상 월 밖 변경은 토큰 지문에 포함하지 않는 설계와 일치하는지 확인한다.
8. 토큰 누락/서명 위조는 400, 업무 데이터 불변. 토큰 안에 원문 참석자 정보를 넣지 않았는지 확인한다.
9. 변동 없는 토큰 재사용은 검증 후 멱등 처리한다. 첫 적용으로 DB 지문이 바뀌었다면 같은 토큰을 무조건 재사용 가능하다고 가정하지 않는다.
10. 중간 실패 시 모든 월의 업무 변경을 롤백하고 별도 트랜잭션의 실패 이력을 검증한다. 인증/입력/토큰 거부 시 실패 이력까지 남길지는 아직 미정이다.
11. 미리보기·반영 각각 EDITOR 성공, VIEWER 403, 미인증 401을 정상 파일로 독립 검증한다. 잘못된 파일과 권한 실패가 겹치는 경우 HTTP 우선순위를 임의로 확정하지 않는다.
12. 누락 파일·빈 파일·손상·xlsm 위장·중복 월·머리글 오류·크기 경계와 초과를 검증한다. 단위 테스트의 byte[] 제한뿐 아니라 실제 multipart 요청 제한도 확인한다.

동시성 테스트는 sleep 대신 latch/barrier를 사용한다. 락은 토큰/DB 버전 검증부터 실제 커밋·롤백 완료까지 유지해야 한다. 미리보기의 차이 계산과 DB 지문 역시 같은 상태에서 산출해야 한다.

## 범위와 남은 합의

KAN-59는 업로드 미리보기/반영, KAN-60은 `GET /api/card-expenses/imports?limit=20` 이력 조회다. GET도 EDITOR 검사를 별도로 적용해야 한다. 이 문서에서는 GET 응답 구조를 새로 확정하지 않는다.

구현 전 확정할 사항: 성공 200, 전부 BLOCKED인 미리보기 응답, 토큰 생략/null, 추가 오류 코드·문구, 만료 경계, 실패 이력 범위, 재활성화 건수(KAN-58), 파일명 처리, 5MB의 정확한 바이트 한도. 기존 설계 문서를 조용히 변경하지 않고 구현 PR에 결정 사항을 함께 반영한다.

현재 검증은 가상 JSON 응답의 문법과 월별 합계 일관성뿐이다. HTTP·인증·토큰·DB 테스트가 통과했다는 뜻이 아니다.
