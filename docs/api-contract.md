# 프론트엔드가 필요한 API 명세

작성일: 2026-09-07 · 수정일: 2026-09-08 · 상태: KAN-27 리뷰 반영본과 정합, 잔여 2건 결정 대기 · 작성: 프론트엔드(한강섭)

## 이 문서의 목적

프론트엔드는 백엔드 API 없이 화면을 먼저 완성했습니다(KAN-30~64, frontend PR #3~#18). `src/api/*` 의 어댑터가 더미 데이터를 돌려주고 있고, 각 함수에 `TODO(KAN-xx 완료 후)` 로 호출할 실제 엔드포인트를 적어 뒀습니다.

**이 문서는 그 TODO 를 모아 놓은 것입니다.** 아래 형태로 API 가 나오면 어댑터 안쪽만 교체하면 되고 화면 코드는 손대지 않습니다.

## 원본과 갱신

**이 문서의 근거는 프론트엔드 저장소의 코드입니다.** 문서와 코드가 어긋나면 코드가 맞습니다.

| 내용 | 원본 위치 (lab-calendar-frontend) |
| --- | --- |
| 도메인 타입 (일정, 과제, 카테고리) | `src/types/domain.ts` |
| 카테고리 키 | `src/constants/categories.ts` |
| 엔드포인트와 요청 형태 | `src/api/*.ts` 의 `TODO(KAN-xx)` 주석 |
| 에러 분류와 재시도 정책 | `src/api/errors.ts`, `src/queries/queryClient.ts` |

프론트 요구사항이 바뀌면 프론트에서 이 문서를 갱신합니다. 백엔드 구현 중 다르게 가야 할 이유를 찾으면 그대로 구현하지 마시고 이슈나 PR 로 알려 주세요.

## 1. 계약 확정 현황

PR #5 리뷰에서 제기한 항목들이 KAN-27 설계 문서에 반영되어 **아래 값으로 확정**되었습니다.

| 항목 | 확정값 | 비고 |
| --- | --- | --- |
| 카테고리 키 | `project` / `lab` / `card` | DB `code` 를 API 에서 `key`, 일정에서는 `categoryKey` 로 반환 |
| 일정 출처 | `MANUAL` / `AUTO_GENERATED` / `GOOGLE_SYNC` | |

## 2. 남은 결정 2건

### 2.1 참석자 동명이인

**현재 프론트 동작**: 참석 인원을 쉼표로 구분한 자유 입력으로 받고, 공백 정리 후 **중복 이름을 제거**합니다 (`parseParticipants`). 그래서 `홍길동, 홍길동` 은 1명이 됩니다.

원래는 같은 이름을 실수로 두 번 넣는 것을 막으려는 처리였는데, 동명이인이 실제로 두 명 있으면 표현하지 못합니다.

**제안: 지금은 현재 동작을 유지하고, KAN-41 에서 연구원 목록 선택 방식으로 바꿀 때 해결합니다.**

자유 입력 상태에서 중복 제거만 없애면, 오타로 같은 이름을 두 번 넣은 것이 그대로 인원수에 반영됩니다. 화면이 `총 N명` 을 배열 길이로 계산하기 때문에 숫자가 틀리게 됩니다. 동명이인은 이름이 아니라 **member ID 로 구분되어야 풀리는 문제**라, 연구원 목록에서 고르는 UI(KAN-41)와 함께 가는 것이 맞습니다.

그때 필요한 것:
- `GET /api/members` — 활성 연구원 목록 (`id`, `name`)
- 일정 요청의 `participants` 를 `memberId[]` + 미등록 인원 이름 배열로 분리

**DB 는 지금 설계대로 동명이인을 허용**하면 됩니다. 프론트가 ID 를 보내기 시작하면 그대로 받으면 됩니다.

### 2.2 제출 단계(`submissionStage`) 필수 여부

**현재 프론트 동작**: 선택 입력입니다. 비워도 과제가 등록되고, 캘린더에는 `BRL 과제` 처럼 과제명만 표시됩니다.

**제안: nullable 유지 (선택 입력).**

- 학회 신청처럼 "제출 단계" 개념이 없는 과제가 있을 수 있습니다
- 필수로 만들면 사용자가 `-` 나 `없음` 같은 값을 채워 넣게 되고, 그 값이 캘린더에 그대로 표시됩니다
- 화면은 값이 없을 때 과제명만 보여주도록 이미 처리돼 있습니다

설계 문서 3장의 "별도 표시가 없으면 NOT NULL" 규칙에 따르면 현재는 NOT NULL 로 읽히므로, **`submission_type` 을 NULL 허용으로 표시**해 주시면 됩니다.

## 3. 프론트가 맞춰야 할 것

**`leadTimeWeeks`(주) → `leadTimeDays`(일) 전환** — 프론트 작업입니다.

현재 프론트는 과제 폼을 주 단위 정수(1~26주)로 받고 `leadTimeWeeks` 로 다룹니다. 백엔드가 일 단위로 확정했으므로 다음을 바꿉니다.

- `Project` / `ProjectInput` 타입 필드명과 단위
- 과제 등록·수정 폼 입력 (주 → 일)
- 검증 범위 — 아래 확인 후 결정
- 더미 어댑터의 준비 기간 계산

**확인 부탁드리는 것 두 가지**

| | 백엔드 | 프론트 현재 | 결정 |
| --- | --- | --- | --- |
| 하한 | 0 이상 | 1주(7일) 이상 | 0일을 허용하면 준비 기간이 마감 당일 하루가 됩니다. 의도한 값인가요? |
| 상한 | 없음 | 26주(182일) | 상한 없이 두면 준비 기간 막대가 캘린더를 덮습니다. 서버에도 상한을 두는 편이 좋아 보입니다 |

프론트는 **0일 허용 / 상한 182일** 정도를 제안합니다. 확정되면 폼 검증을 맞추겠습니다. 별도 프론트 이슈로 진행하고 이 문서에 반영합니다.

## 4. 공통 규약

### 4.1 Base URL 과 로컬 개발

- **운영**: nginx 가 `/api/` 를 `backend:8080` 으로 프록시합니다. 프론트는 같은 오리진 상대 경로로 호출하므로 **CORS 설정이 필요 없습니다**.
- **로컬 개발**: 프론트 dev 서버는 `:5173`, 백엔드는 `:8080` 이라 교차 오리진입니다.

**제안: 프론트 Vite dev proxy 로 `/api` 를 `localhost:8080` 에 넘깁니다.** 그러면 개발에서도 같은 오리진이 되어 **백엔드에 개발 전용 CORS 설정이 필요 없습니다.** 운영과 요청 형태도 같아집니다. 프론트 쪽 변경이므로 연동 시작 전에 넣어 두겠습니다.

### 4.2 응답 포맷

프론트는 공통 래퍼를 가정하고 있습니다 (KAN-29).

```json
{ "data": { } }
```

목록은 `data` 가 배열입니다. **아직 확정되지 않은 항목입니다.** 래퍼 형태가 다르면 어댑터에서 변환하므로 정해서 알려만 주시면 됩니다.

### 4.3 날짜와 시간대

- 모든 날짜는 `YYYY-MM-DD` 문자열입니다.
- **`endDate` 는 화면에 표시되는 마지막 날이며 포함입니다.** 하루짜리 일정은 `startDate === endDate` 입니다.
- **조회 기간 `from` / `to` 도 양끝 포함입니다.** 겹침 판정은 `startDate <= to && endDate >= from` 입니다.
- 시간대는 `Asia/Seoul` 기준입니다.
- **1차 API 는 종일 일정만 다룹니다.** 프론트에 시간(시:분) 개념이 없습니다.

FullCalendar 의 배타적 `end` 변환은 프론트 `eventDates.ts` 경계에서만 수행합니다. 서버는 관여하지 않습니다.

### 4.4 에러 응답

프론트는 HTTP 상태 코드로 에러를 분류하고, 본문의 `message` 를 사용자에게 그대로 보여줍니다.

| 상태 | 프론트 분류 | 화면 처리 |
| --- | --- | --- |
| 400, 422 | `VALIDATION` | 재시도 안 함. `fieldErrors` 가 있으면 필드에 표시 |
| 401 | `UNAUTHORIZED` | 재시도 안 함. 비밀번호 재입력 안내 |
| 403 | `FORBIDDEN` | 재시도 안 함 |
| 404 | `NOT_FOUND` | 재시도 안 함 |
| 5xx | `SERVER` | 최대 2회 재시도 |
| 응답 없음 | `NETWORK` | 최대 2회 재시도 |

```json
{
  "message": "사용자에게 보여줄 문구",
  "fieldErrors": { "title": "제목을 입력해 주세요." }
}
```

`message` 는 화면에 그대로 노출되므로 내부 예외 메시지나 스택은 넣지 말아 주세요. `fieldErrors` 의 키는 요청 본문의 필드명과 같아야 합니다.

자동/구글 일정에 대한 쓰기 거부는 **403** 으로 내려 주시면 프론트가 재시도하지 않습니다.

## 5. 카테고리 (KAN-38)

### GET /api/categories

```json
{
  "data": [
    { "id": 1, "key": "project", "name": "과제/연구 관리" },
    { "id": 2, "key": "lab",     "name": "랩실 주기적 일정" },
    { "id": 3, "key": "card",    "name": "카드/경비 사용" }
  ]
}
```

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `id` | number | |
| `key` | string | `project` \| `lab` \| `card` |
| `name` | string | 표시 이름. 프론트는 이 값을 그대로 씁니다 |

**`key` 는 프론트의 하드코딩 계약입니다.** `tokens.css` 의 `[data-category]` 셀렉터, URL 필터 파라미터(`?categories=project,lab`)에 그대로 들어갑니다.

**색상은 내려주지 않습니다.** 프론트 디자인 토큰에서 관리하며 명도 대비 4.5:1 기준으로 고른 값입니다(KAN-64, 회귀 테스트 있음).

**VIEWER 등급**은 서버가 이 응답에서 `card` 를 빼 주세요 (KAN-35).

## 6. 일정 (KAN-39, KAN-40)

### 6.1 일정 객체

```json
{
  "id": "12",
  "title": "BRL 과제",
  "detail": "연차보고서",
  "startDate": "2026-09-05",
  "endDate": "2026-09-26",
  "categoryKey": "project",
  "memo": "마감 3주 전부터 자동 생성된 준비 기간입니다.",
  "participants": ["홍길동", "김철수"],
  "source": "AUTO_GENERATED"
}
```

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `id` | string | ✅ | |
| `title` | string | ✅ | 과제명 / 업무명 / 카드 종류 |
| `detail` | string \| null | | 카테고리별로 의미가 다름 (6.2) |
| `startDate` | `YYYY-MM-DD` | ✅ | |
| `endDate` | `YYYY-MM-DD` | ✅ | **표시 마지막 날, 포함** |
| `categoryKey` | string | ✅ | `project` \| `lab` \| `card` |
| `memo` | string \| null | | |
| `participants` | string[] | ✅ | `position` 순 이름 배열. 빈 배열 허용 |
| `source` | string | ✅ | `MANUAL` \| `AUTO_GENERATED` \| `GOOGLE_SYNC` |

### 6.2 `detail` 조합

프론트는 `detail` **필드 하나**로 달력 칩과 상세 팝업을 그립니다 (기획서 2.2 표시 양식).

| 카테고리 | `detail` | 화면 표기 |
| --- | --- | --- |
| `project` | 제출 단계 | `BRL 과제 (연차보고서)` |
| `lab` | 담당 연구원 | `정기 주간 랩미팅 (홍길동)` |
| `card` | 사용 목적 | `[법인카드 A]: 다과비` |

서버 조합 규칙은 설계 문서 5.1 절과 같습니다. 요약하면:

| 일정 종류 | `title` | `detail` |
| --- | --- | --- |
| AUTO_GENERATED | `research_project.name` | `research_project.submission_type` |
| GOOGLE_SYNC | `card_expense.card_name` | `card_expense.purpose` |
| MANUAL (담당자 연결된 lab) | `event.title` | `member.name` |
| MANUAL (그 외) | `event.title` | `event.manual_detail` |

**프론트는 `detail` 을 그냥 문자열로 보냅니다.** 수동 일정 등록·수정 시 `detail` 에 사용자가 입력한 값이 그대로 들어가며, 서버가 `manual_detail` 에 저장하면 됩니다. 프론트는 `owner_member_id` 를 보내지 않으므로 설계 문서에 적힌 "자유 입력 detail 과 담당자 충돌" 은 현재 발생하지 않습니다.

### 6.3 `source` 와 수정 권한

**`MANUAL` 인 일정만 수정·삭제·드래그를 허용합니다.**

| `source` | 프론트 동작 |
| --- | --- |
| `MANUAL` | 수정·삭제·드래그 가능 |
| `AUTO_GENERATED` | 버튼 숨김. "과제 관리에서 종료일/리드타임을 바꾸세요" 안내 |
| `GOOGLE_SYNC` | 버튼 숨김. "원본 문서를 수정하세요" 안내 |

서버도 같은 규칙으로 막습니다(설계 문서 반영 완료). 프론트에서 감추는 건 편의일 뿐 정합성 경계가 아닙니다.

### 6.4 GET /api/events

| 파라미터 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `from` | `YYYY-MM-DD` | ✅ | 조회 시작일, **포함** |
| `to` | `YYYY-MM-DD` | ✅ | 조회 종료일, **포함** |

프론트는 달력이 표시하는 기간(앞뒤 달 걸침 포함)을 그대로 보냅니다. 예: 2026년 9월 화면 → `from=2026-08-30&to=2026-10-03`

**카테고리 필터는 파라미터로 보내지 않습니다.** 받아둔 목록을 화면에서 거릅니다(KAN-43 완료 조건 — 필터 변경 시 재조회 없음). 서버에 `categoryIds` 파라미터가 있어도 프론트는 쓰지 않습니다.

**응답**: `{ "data": [ 일정 객체, ... ] }` — 기간에 **겹치는** 일정을 모두 포함합니다.

**VIEWER 등급**은 서버가 `card` 카테고리와 `GOOGLE_SYNC` 출처 일정을 제외해 주세요.

### 6.5 POST /api/events

일정 객체에서 `id` 와 `source` 를 뺀 형태입니다. `source` 는 서버가 `MANUAL` 로 정합니다.

```json
{
  "title": "정기 주간 랩미팅",
  "detail": "홍길동",
  "startDate": "2026-09-10",
  "endDate": "2026-09-10",
  "categoryKey": "lab",
  "memo": null,
  "participants": ["홍길동", "김철수"]
}
```

**응답**: `{ "data": 생성된 일정 객체 }`

**검증 규칙** — 프론트도 같은 규칙으로 먼저 막지만 서버 검증이 최종입니다.

- `title` 은 공백만 있으면 안 됩니다
- `endDate >= startDate`
- `participants` 는 공백 제거 후 중복 제거된 이름 배열입니다 (2.1 참고)

### 6.6 PUT /api/events/{id}

요청 본문은 POST 와 같고, 응답은 수정된 일정 객체입니다.

**드래그로 기간을 옮길 때도 이 엔드포인트를 씁니다.** 이때는 `startDate` / `endDate` 만 바뀌고 나머지는 기존 값 그대로 다시 보냅니다.

`source` 가 `MANUAL` 이 아니면 **403** 으로 거부해 주세요.

### 6.7 DELETE /api/events/{id}

성공 시 본문 없이 2xx. `source` 가 `MANUAL` 이 아니면 **403**.

## 7. 과제 (KAN-47, KAN-48)

### 7.1 과제 객체

```json
{
  "id": "3",
  "name": "BRL 과제",
  "submissionStage": "연차보고서",
  "endDate": "2026-09-26",
  "leadTimeDays": 21,
  "active": true,
  "dDay": 20,
  "preparationStartDate": "2026-09-05"
}
```

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `id` | string | ✅ | |
| `name` | string | ✅ | 과제명 |
| `submissionStage` | string \| null | | 제출 단계. 일정의 `detail` 로 쓰입니다 (2.2 참고) |
| `endDate` | `YYYY-MM-DD` | ✅ | 제출 마감일, 포함 |
| `leadTimeDays` | number | ✅ | 준비 기간(일). 기본 21 |
| `active` | boolean | ✅ | false 면 준비 기간 일정을 캘린더에서 제외 |
| `dDay` | number | ✅ | **서버 계산값** (7.2) |
| `preparationStartDate` | `YYYY-MM-DD` | ✅ | **서버 계산값.** `endDate - leadTimeDays` |

### 7.2 서버가 계산해서 내려줘야 하는 값

**`dDay` 와 `preparationStartDate` 는 프론트에서 다시 계산하지 않습니다.**

`dDay` 는 서버의 `Asia/Seoul` 자정 기준 마감까지 남은 일수입니다. 당일은 `0`, 지난 과제는 음수입니다. 화면에서 계산하면 기기 시계나 타임존에 따라 사람마다 다른 D-Day 를 보게 됩니다 (KAN-52 완료 조건).

**KAN-52 D-Day 위젯에 별도 엔드포인트는 필요 없습니다.** 이 목록이 `dDay` 를 포함하고 마감순으로 정렬돼 오면 프론트가 상위 N건을 잘라 씁니다.

### 7.3 과제와 준비 기간 일정

- 과제를 저장하면 서버가 준비 기간 일정을 만들거나 갱신합니다 (KAN-49 배치).
- `active = false` 인 과제의 준비 기간 일정은 **일정 조회 응답에서 빠져야** 합니다.
- `endDate` 나 `leadTimeDays` 가 바뀌면 준비 기간 일정도 함께 갱신되어야 합니다.

프론트는 과제를 저장·삭제한 뒤 **일정 쿼리도 함께 무효화**하므로, 서버가 일정을 다시 만들어 두면 화면은 바로 따라옵니다.

### 7.4 엔드포인트

| 메서드 | 경로 | 요청 본문 | 응답 |
| --- | --- | --- | --- |
| GET | `/api/projects` | — | `{ "data": [과제 객체] }` |
| POST | `/api/projects` | 과제 입력값 | `{ "data": 과제 객체 }` |
| PUT | `/api/projects/{id}` | 과제 입력값 | `{ "data": 과제 객체 }` |
| DELETE | `/api/projects/{id}` | — | 본문 없이 2xx |

**과제 입력값** = 과제 객체에서 `id`, `dDay`, `preparationStartDate` 를 뺀 것

```json
{
  "name": "BRL 과제",
  "submissionStage": "연차보고서",
  "endDate": "2026-09-26",
  "leadTimeDays": 21,
  "active": true
}
```

**목록 정렬**: 마감이 이른 순, 비활성 과제는 뒤로.

**검증 규칙**: `name` 공백 불가, `endDate` 필수, `leadTimeDays` 범위는 3절 확정 후.

## 8. 아직 정의되지 않은 것

### 8.1 인증 (KAN-21, KAN-34~37)

프론트는 아직 구현하지 않았습니다. 준비된 것:

- 401 응답을 `UNAUTHORIZED` 로 분류하고 재시도하지 않습니다
- 등급은 **EDITOR(편집)** / **VIEWER(조회 전용)** 두 가지로 결정했습니다
- **VIEWER 는 카드/경비 데이터를 서버가 응답에서 빼야 합니다.** 외부 자문 위원에게 지출 내역이 보이지 않게 하는 것이 이 등급의 목적입니다

정해야 할 것: 로그인 엔드포인트, 세션 유지 방식(쿠키/토큰), 등급 전달 방식, 만료 시 재인증 흐름. 백엔드에서 정해 주시면 프론트가 맞추겠습니다.

### 8.2 카드/경비 동기화 (KAN-58, KAN-61)

KAN-54(구글 Docs/Sheets 소스 확정)가 정해진 뒤입니다. 프론트 화면(KAN-61)에 필요한 것:

- 수동 동기화 트리거 엔드포인트
- 마지막 동기화 시각과 결과 상태 (성공 / 부분 실패 / 실패)
- 실패 시 사용자에게 보여줄 사유

설계의 `sync_log` 에 필요한 데이터가 다 있어서 조회 엔드포인트만 열어 주시면 됩니다.

### 8.3 연구원 목록 (KAN-41)

참석자를 이름 자유 입력에서 목록 선택으로 바꿀 때 필요합니다 (2.1 참고). 지금은 없어도 됩니다.

## 9. 연동 순서 제안

프론트는 어댑터 단위로 붙일 수 있어서 한꺼번에 갈 필요가 없습니다.

1. **카테고리** (KAN-38) — 가장 단순하고 응답 래퍼·에러 포맷을 먼저 확인할 수 있습니다
2. **일정 조회** (KAN-40) — 달력이 실제 데이터로 그려집니다
3. **일정 CRUD** (KAN-39)
4. **과제** (KAN-47, KAN-48) — 준비 기간 자동 생성까지
5. **인증** (KAN-21, KAN-34~37)
6. **카드 동기화** (KAN-58, KAN-61)

각 단계에서 프론트가 바꾸는 건 `src/api/` 안의 해당 함수 하나뿐이고, 화면·쿼리 훅·테스트는 그대로입니다.
