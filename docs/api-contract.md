# 프론트엔드가 필요한 API 명세

작성일: 2026-09-07 · 상태: 합의 대기 · 작성: 프론트엔드(한강섭)

## 이 문서의 목적

프론트엔드는 백엔드 API 없이 화면을 먼저 완성했습니다(KAN-30~64, frontend PR #3~#18). `src/api/*` 의 어댑터가 더미 데이터를 돌려주고 있고, 각 함수에 `TODO(KAN-xx 완료 후)` 로 호출할 실제 엔드포인트를 적어 뒀습니다.

**이 문서는 그 TODO 를 모아 놓은 것입니다.** 아래 형태로 API 가 나오면 어댑터 안쪽만 교체하면 되고 화면 코드는 손대지 않습니다.

## 원본과 갱신

**이 문서의 근거는 프론트엔드 저장소의 코드입니다.** 문서와 코드가 어긋나면 코드가 맞습니다.

| 내용 | 원본 위치 (lab-calendar-frontend) |
| --- | --- |
| 도메인 타입 (일정, 과제, 카테고리) | `src/types/domain.ts` |
| 카테고리 키 | `src/constants/categories.ts` |
| 엔드포인트와 요청 형태 | `src/api/*.ts` 의 `TODO(KAN-xx)` 주석 |
| 에러 분류와 재시도 정책 | `src/api/errors.ts`, `src/queries/queryClient.ts` |

프론트 요구사항이 바뀌면 프론트에서 이 문서를 갱신합니다. 백엔드 구현 중 다르게 가야 할 이유를 찾으면 그대로 구현하지 마시고 이슈나 PR 로 알려 주세요 — 프론트가 맞추면 되는 경우가 대부분입니다.

## 1. 합의가 필요한 항목 (먼저 읽어 주세요)

backend PR #5 리뷰에서 제기한 것들입니다. **이 네 가지가 정해져야 아래 명세가 확정됩니다.**

| # | 항목 | 프론트 현재 | ERD 초안 | 비고 |
| --- | --- | --- | --- | --- |
| 1 | 카테고리 키 | `project` / `lab` / `card` | `RESEARCH` / `LAB` / `CARD_EXPENSE` | 프론트는 이 값을 CSS 셀렉터와 URL 파라미터에 사용 |
| 2 | 일정 출처 | `MANUAL` / `AUTO_GENERATED` / `GOOGLE_SYNC` | `MANUAL` / `PROJECT` / `GOOGLE` | 수정 가능 여부 판단에 사용 |
| 3 | 날짜 범위 | 양끝 **포함** | `[from, to)` 제안 | 아래 2.3 |
| 4 | 리드타임 단위 | 주(week) | 일(day) 저장 | API 노출 단위를 정해야 함 |

아래 명세는 **프론트의 현재 계약**을 기준으로 적었습니다. 합의 결과에 따라 바뀌는 부분은 각 절에 표시했습니다.

## 2. 공통 규약

### 2.1 Base URL

프론트는 `VITE_API_BASE_URL` 환경변수로 받습니다. 개발 기본값은 `http://localhost:8080` 입니다.

### 2.2 응답 포맷

프론트는 공통 래퍼를 가정하고 있습니다 (KAN-29).

```json
{ "data": { } }
```

목록은 `data` 가 배열입니다. 래퍼 형태가 다르면 어댑터에서 변환하므로 **확정만 해 주시면 됩니다.**

### 2.3 날짜와 시간대

- 모든 날짜는 `YYYY-MM-DD` 문자열입니다.
- **일정의 `endDate` 는 화면에 표시되는 마지막 날이며 포함입니다.** 하루짜리 일정은 `startDate === endDate` 입니다.
- **조회 기간 `from` / `to` 도 양끝 포함입니다.** 겹침 판정은 `startDate <= to && endDate >= from` 입니다.
- 시간대는 `Asia/Seoul` 기준입니다.
- 프론트에 시간(시:분) 개념은 없습니다. 모든 일정이 종일입니다.

> **합의 항목 3.** ERD 초안은 조회에 `[from, to)` 를 제안했습니다. 프론트는 FullCalendar 의 배타적 `end` 를 컴포넌트 경계에서 이미 포함 형식으로 변환하고 있어, API 까지 제외 규약을 쓰면 변환 지점이 둘이 됩니다(하루 밀림 버그가 났던 자리입니다). 양끝 포함을 제안합니다.

### 2.4 에러 응답

프론트는 HTTP 상태 코드로 에러를 분류하고, 본문의 `message` 를 사용자에게 그대로 보여줍니다.

| 상태 | 프론트 분류 | 화면 처리 |
| --- | --- | --- |
| 400, 422 | `VALIDATION` | 재시도 안 함. `fieldErrors` 가 있으면 필드에 표시 |
| 401 | `UNAUTHORIZED` | 재시도 안 함. 비밀번호 재입력 안내 |
| 403 | `FORBIDDEN` | 재시도 안 함 |
| 404 | `NOT_FOUND` | 재시도 안 함 |
| 5xx | `SERVER` | 최대 2회 재시도 |
| 응답 없음 | `NETWORK` | 최대 2회 재시도 |

에러 본문:

```json
{
  "message": "사용자에게 보여줄 문구",
  "fieldErrors": { "title": "제목을 입력해 주세요." }
}
```

`message` 는 화면에 그대로 노출되므로 내부 예외 메시지나 스택은 넣지 말아 주세요. `fieldErrors` 의 키는 요청 본문의 필드명과 같아야 합니다.

## 3. 카테고리 (KAN-38)

### GET /api/categories

카테고리 목록. 프론트는 이 응답으로 좌측 필터를 그립니다.

**응답**

```json
{
  "data": [
    { "id": 1, "key": "project", "name": "과제/연구 관리" },
    { "id": 2, "key": "lab",     "name": "랩실 주기적 일정" },
    { "id": 3, "key": "card",    "name": "카드/경비 사용" }
  ]
}
```

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `id` | number | |
| `key` | string | **`project` \| `lab` \| `card`** — 합의 항목 1 |
| `name` | string | 표시 이름. 프론트는 이 값을 그대로 씁니다 |

**중요한 점 두 가지**

- **`key` 는 프론트의 하드코딩 계약입니다.** `tokens.css` 의 `[data-category]` 셀렉터, URL 필터 파라미터(`?categories=project,lab`)에 그대로 들어갑니다.
- **표시 색상은 내려주지 않아도 됩니다.** 색은 프론트 디자인 토큰에 있고, 명도 대비 4.5:1 기준으로 고른 값입니다(KAN-64, 회귀 테스트 있음). 응답에 색이 있어도 프론트는 쓰지 않습니다.

**VIEWER 등급**은 서버가 이 응답에서 `card` 를 빼 주세요 (KAN-35). 그러면 필터 목록에서도 자연스럽게 사라집니다.

## 4. 일정 (KAN-39, KAN-40)

### 4.1 일정 객체

프론트가 다루는 형태입니다.

```json
{
  "id": "12",
  "title": "BRL 과제",
  "detail": "연차보고서",
  "startDate": "2026-09-05",
  "endDate": "2026-09-26",
  "categoryKey": "project",
  "memo": "마감 3주 전부터 자동 생성된 준비 기간입니다.",
  "participants": ["홍길동", "김철수"],
  "source": "AUTO_GENERATED"
}
```

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `id` | string | ✅ | |
| `title` | string | ✅ | 주 제목 — 과제명 / 업무명 / 카드 종류 |
| `detail` | string \| null | | 카테고리별로 의미가 다름. 아래 참고 |
| `startDate` | `YYYY-MM-DD` | ✅ | |
| `endDate` | `YYYY-MM-DD` | ✅ | **표시 마지막 날, 포함** |
| `categoryKey` | string | ✅ | `project` \| `lab` \| `card` |
| `memo` | string \| null | | |
| `participants` | string[] | ✅ | 이름 배열. 빈 배열 허용 |
| `source` | string | ✅ | `MANUAL` \| `AUTO_GENERATED` \| `GOOGLE_SYNC` |

### 4.2 `detail` 은 서버가 조합해서 내려주세요

프론트는 `detail` **필드 하나**로 달력 칩과 상세 팝업을 그립니다 (기획서 2.2 표시 양식).

| 카테고리 | `detail` 에 들어갈 값 | 화면 표기 |
| --- | --- | --- |
| `project` | 제출 단계 | `BRL 과제 (연차보고서)` |
| `lab` | 담당 연구원 | `정기 주간 랩미팅 (홍길동)` |
| `card` | 사용 목적 | `[법인카드 A]: 다과비` |

ERD 초안에서는 이 값이 `research_project.submission_type`, `member.name`, `card_expense.purpose` 로 흩어져 있습니다. **목록 응답에서 조합해 주세요.** 안 그러면 프론트가 칩 하나 그리려고 과제·연구원·카드를 따로 조회해야 합니다.

같은 이유로 **과제 자동 생성 일정도 `title` 과 `detail` 을 분리**해 주세요. ERD 초안의 `title_template`(`[작성 요망] {과제명} {제출단계} 준비 시작`)을 `title` 에 넣으면 화면에 `[작성 요망] BRL 과제 연차보고서 준비 시작 (연차보고서)` 로 나옵니다.

### 4.3 `source` 와 수정 권한

**`MANUAL` 인 일정만 수정·삭제·드래그를 허용합니다.** (KAN-39 코멘트에서 합의)

| `source` | 의미 | 프론트 동작 |
| --- | --- | --- |
| `MANUAL` | 사람이 직접 등록 | 수정·삭제·드래그 가능 |
| `AUTO_GENERATED` | 과제 리드타임 배치 생성 (KAN-49) | 버튼 숨김. "과제 관리에서 종료일/리드타임을 바꾸세요" 안내 |
| `GOOGLE_SYNC` | 구글 문서 동기화 (KAN-58) | 버튼 숨김. "원본 문서를 수정하세요" 안내 |

**서버도 같은 규칙으로 막아 주세요.** `AUTO_GENERATED` / `GOOGLE_SYNC` 에 대한 `PUT` · `DELETE` 는 거부해야 합니다. 프론트에서 감추는 건 편의일 뿐 정합성 경계가 아닙니다. 고쳐도 다음 배치·동기화가 덮어써서 조용히 되돌아가기 때문입니다.

### 4.4 GET /api/events

**요청**

| 파라미터 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `from` | `YYYY-MM-DD` | ✅ | 조회 시작일, **포함** |
| `to` | `YYYY-MM-DD` | ✅ | 조회 종료일, **포함** |

프론트는 달력이 표시하는 기간(앞뒤 달 걸침 포함)을 그대로 보냅니다. 예: 2026년 9월 화면 → `from=2026-08-30&to=2026-10-03`

**카테고리 필터는 파라미터로 보내지 않습니다.** 한 달치는 양이 적어 받아둔 목록을 화면에서 거르는 편이 빠르고, 필터를 바꿀 때마다 재조회하지 않기 위해서입니다(KAN-43 완료 조건). 서버에 `categoryIds` 파라미터가 있어도 프론트는 쓰지 않습니다.

**응답**: `{ "data": [ 일정 객체, ... ] }`

기간에 **겹치는** 일정을 모두 포함합니다. 기간을 벗어나 시작하거나 끝나는 일정도 걸쳐 있으면 포함입니다.

**VIEWER 등급**은 서버가 `card` 카테고리와 `GOOGLE_SYNC` 출처 일정을 제외해 주세요 (KAN-35). 목록뿐 아니라 단건 조회에도 같은 정책이 필요합니다.

### 4.5 POST /api/events

**요청 본문** — 일정 객체에서 `id` 와 `source` 를 뺀 형태입니다. `source` 는 서버가 `MANUAL` 로 정합니다.

```json
{
  "title": "정기 주간 랩미팅",
  "detail": "홍길동",
  "startDate": "2026-09-10",
  "endDate": "2026-09-10",
  "categoryKey": "lab",
  "memo": null,
  "participants": ["홍길동", "김철수"]
}
```

**응답**: `{ "data": 생성된 일정 객체 }` (`id`, `source` 포함)

**검증 규칙** — 프론트도 같은 규칙으로 먼저 막지만, 서버 검증이 최종입니다.

- `title` 은 공백만 있으면 안 됩니다
- `endDate >= startDate`
- `participants` 는 공백 제거 후 중복 제거된 이름 배열입니다

### 4.6 PUT /api/events/{id}

요청 본문은 POST 와 같습니다. 응답은 수정된 일정 객체입니다.

**드래그로 기간을 옮길 때도 이 엔드포인트를 씁니다.** 이때는 `startDate` / `endDate` 만 바뀌고 나머지는 기존 값 그대로 다시 보냅니다.

`source` 가 `MANUAL` 이 아니면 **거부**해 주세요 (4.3).

### 4.7 DELETE /api/events/{id}

성공 시 본문 없이 2xx. `source` 가 `MANUAL` 이 아니면 **거부**해 주세요.

## 5. 과제 (KAN-47, KAN-48)

### 5.1 과제 객체

```json
{
  "id": "3",
  "name": "BRL 과제",
  "submissionStage": "연차보고서",
  "endDate": "2026-09-26",
  "leadTimeWeeks": 3,
  "active": true,
  "dDay": 20,
  "preparationStartDate": "2026-09-05"
}
```

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `id` | string | ✅ | |
| `name` | string | ✅ | 과제명 |
| `submissionStage` | string \| null | | 제출 단계. 일정의 `detail` 로 쓰입니다 |
| `endDate` | `YYYY-MM-DD` | ✅ | 제출 마감일, 포함 |
| `leadTimeWeeks` | number | ✅ | 준비 기간(주). 기본 3 — **합의 항목 4** |
| `active` | boolean | ✅ | false 면 준비 기간 일정을 캘린더에서 제외 |
| `dDay` | number | ✅ | **서버 계산값.** 아래 참고 |
| `preparationStartDate` | `YYYY-MM-DD` | ✅ | **서버 계산값.** `endDate - leadTime` |

### 5.2 서버가 계산해서 내려줘야 하는 값

**`dDay` 와 `preparationStartDate` 는 프론트에서 다시 계산하지 않습니다.**

`dDay` 는 서버의 `Asia/Seoul` 자정 기준 마감까지 남은 일수입니다. 당일은 `0`, 지난 과제는 음수입니다. 화면에서 계산하면 기기 시계나 타임존에 따라 사람마다 다른 D-Day 를 보게 됩니다 (KAN-52 완료 조건).

### 5.3 과제와 준비 기간 일정

- 과제를 저장하면 서버가 준비 기간 일정을 만들거나 갱신합니다 (KAN-49 배치).
- `active = false` 인 과제의 준비 기간 일정은 **일정 조회 응답에서 빠져야** 합니다. 과제를 지우지 않고 캘린더에서만 감추는 용도입니다.
- `endDate` 나 리드타임이 바뀌면 준비 기간 일정도 함께 갱신되어야 합니다.

프론트는 과제를 저장·삭제한 뒤 **일정 쿼리도 함께 무효화**하도록 되어 있어, 서버가 일정을 다시 만들어 두면 화면은 바로 따라옵니다.

### 5.4 엔드포인트

| 메서드 | 경로 | 요청 본문 | 응답 |
| --- | --- | --- | --- |
| GET | `/api/projects` | — | `{ "data": [과제 객체] }` |
| POST | `/api/projects` | 과제 입력값 | `{ "data": 과제 객체 }` |
| PUT | `/api/projects/{id}` | 과제 입력값 | `{ "data": 과제 객체 }` |
| DELETE | `/api/projects/{id}` | — | 본문 없이 2xx |

**과제 입력값** = 과제 객체에서 `id`, `dDay`, `preparationStartDate` 를 뺀 것

```json
{
  "name": "BRL 과제",
  "submissionStage": "연차보고서",
  "endDate": "2026-09-26",
  "leadTimeWeeks": 3,
  "active": true
}
```

**목록 정렬**: 마감이 이른 순, 비활성 과제는 뒤로. (프론트에서도 정렬하지만 서버가 정렬해 주면 그대로 씁니다)

**검증 규칙**: `name` 공백 불가, `endDate` 필수, 리드타임은 1~26주 정수

## 6. 아직 정의되지 않은 것

### 6.1 인증 (KAN-21, KAN-34~37)

프론트는 아직 구현하지 않았습니다. 다만 다음은 이미 준비돼 있습니다.

- 401 응답을 `UNAUTHORIZED` 로 분류하고 재시도하지 않습니다
- 등급은 **EDITOR(편집)** / **VIEWER(조회 전용)** 두 가지로 결정했습니다
- **VIEWER 는 카드/경비 데이터를 서버가 응답에서 빼야 합니다.** 화면에서 숨기는 것으로는 안 됩니다 — 외부 자문 위원에게 지출 내역이 보이지 않게 하는 것이 이 등급의 목적이기 때문입니다

로그인 엔드포인트, 세션 유지 방식(쿠키/토큰), 등급 전달 방식은 백엔드에서 정해 주시면 프론트가 맞추겠습니다.

### 6.2 카드/경비 동기화 (KAN-58, KAN-61)

KAN-54(구글 Docs/Sheets 소스 확정)가 정해진 뒤입니다. 프론트 화면(KAN-61)에 필요한 것은 다음과 같습니다.

- 수동 동기화 트리거 엔드포인트
- 마지막 동기화 시각과 결과 상태 (성공 / 부분 실패 / 실패)
- 실패 시 사용자에게 보여줄 사유

ERD 초안의 `sync_log` 에 필요한 데이터가 다 있어서, 조회 엔드포인트만 열어 주시면 됩니다.

### 6.3 시간 지정 일정

ERD 초안에 `all_day` / `start_time` / `end_time` 이 있는데 **프론트에는 시간 개념이 없습니다.** 1.1.0 범위인지 확인이 필요합니다. 범위라면 프론트 이슈를 따로 만들어야 하고, 아니라면 API·검증은 후속으로 미루는 편이 안전합니다. 지금 상태로 서버만 시간을 받으면 사용자가 지정한 시간이 화면에서 사라집니다.

## 7. 연동 순서 제안

프론트는 어댑터 단위로 붙일 수 있어서 한꺼번에 갈 필요가 없습니다.

1. **카테고리** (KAN-38) — 가장 단순하고 응답 래퍼·에러 포맷을 먼저 확인할 수 있습니다
2. **일정 조회** (KAN-40) — 달력이 실제 데이터로 그려집니다
3. **일정 CRUD** (KAN-39) — 등록·수정·삭제
4. **과제** (KAN-47, KAN-48) — 준비 기간 자동 생성까지
5. **인증** (KAN-21, KAN-34~37)
6. **카드 동기화** (KAN-58, KAN-61)

각 단계에서 프론트가 바꾸는 건 `src/api/` 안의 해당 함수 하나뿐이고, 화면·쿼리 훅·테스트는 그대로입니다.
