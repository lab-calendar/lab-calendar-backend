# KAN-58 월별 반영 테스트 준비

기준: 머지된 KAN-54 §3.1·3.2·7.1, KAN-57의 READY/BLOCKED 결과. **예상 결과 자료만 준비했으며 동기화 서비스·DB 변경·실행 가능한 서비스 테스트는 아직 구현하지 않았다.** KAN-56·57 리뷰 반영 후 실제 서비스 테스트에 연결한다.

## 가상 데이터와 파일

`src/test/resources/expense/importing/month-sync-cases.json`에 12개 사례를 저장했다. A/B는 9월의 서로 다른 가상 기록, C/D는 8월 기록, A2는 A의 참석자가 변경된 기록, W는 참석자가 없는 경고 기록이다. A#1/A#2는 내용이 완전히 같은 두 행이다. 키는 월 안에서만 의미가 있는 기호이며 실제 해시·DB ID가 아니다. 사용자 원본 파일이나 실명은 사용하지 않는다.

before/afterActiveByMonth는 활성 내역 목록이다. 기존 일정은 각 활성 내역에 하나씩 있다고 가정한다. deleteEventKeys에 든 일정은 참석자 연결까지 삭제하고, 같은 키의 card_expense는 물리 삭제하지 않고 inactive로 남긴다. preserveEventKeys는 event ID와 참석자 내용을 유지해야 한다는 뜻이다. 실제 저장 테스트에서는 키를 DB ID로 매핑하여 검증한다.

| 사례 ID | 기대 동작 | 추가 / 제거 / 동일 |
| --- | --- | --- |
| first_import | A 내역·일정 생성 | 1 / 0 / 0 |
| same_file_again | A와 일정 ID 유지, 중복 없음 | 0 / 0 / 1 |
| missing_record | B 비활성화·일정 및 일정 참석자 삭제, A 유지 | 0 / 1 / 1 |
| absent_month | 입력에 없는 8월 C 보존, 9월만 비교 | 0 / 0 / 1 |
| blocked_month | 오류 월의 A·B와 일정·참석자 모두 보존 | 0 / 0 / 0 |
| valid_empty_month | 정상 빈 월의 A·B 비활성화와 일정 삭제 | 0 / 2 / 0 |
| error_empty_month | 오류로 비어 있는 월의 A·B 보존 | 0 / 0 / 0 |
| partial_months | 8월 D만 추가, 오류가 있는 9월 전체 보존 | 1 / 0 / 1 |
| changed_content | A 비활성화·일정 삭제, A2 새 내역·일정 생성 | 1 / 1 / 0 |
| warning_only | 경고만 있는 W는 반영 가능, 참석자 0명 | 1 / 0 / 0 |
| duplicate_rows | 같은 내용도 두 건으로 유지 | 2 / 0 / 0 |
| one_duplicate_removed | 두 건 중 한 건만 비활성화 | 0 / 1 / 1 |

BLOCKED 월의 0건은 기존 데이터가 없다는 뜻이 아니다. 입력에 없는 달은 동일 건수에도 포함하지 않는다. 모든 월 BLOCKED는 적용 거부(NO_APPLICABLE_MONTHS), READY와 BLOCKED 혼합은 PARTIAL 이력 대상이다. HTTP 422 검증은 업로드 API 연결 시 수행한다.

## 상태를 가진 추가 통합 테스트

다음은 단순 활성 목록 비교로 검증할 수 없어 서비스·DB 구현 후 별도 테스트한다.

1. **재등장**: A를 반영 → 빈 READY 월로 비활성화 → A 재업로드. 동일 card_expense 행과 원본 키를 재활성화하고 일정 하나를 다시 생성한다. 삭제된 일정의 ID 복구는 요구하지 않는다. 재활성화를 added로 셀지 별도 건수로 표시할지는 설계에 명시되지 않아 리뷰에서 확정한다.
2. **미리보기**: 제거 대상이 있어도 card_expense/event/event_participant와 이력 테이블에 아무 쓰기도 없어야 한다. 반영 확인 뒤에만 변경한다.
3. **원자성**: 두 READY 월 중 두 번째 월 처리 시 강제로 실패시킨다. 첫 월의 생성·비활성화·일정/참석자 삭제까지 전부 롤백하고 별도 트랜잭션의 실패 이력만 남긴다.
4. **경합**: 두 반영 요청을 barrier/latch로 겹치게 하고 버전 확인부터 커밋까지 직렬 처리되는지 확인한다. 단순 UNIQUE 충돌 검증만으로 대체하지 않는다. 오래된 미리보기 토큰의 409는 KAN-59 통합 테스트와 연결한다.
5. **두 번 반영**: 같은 파일을 두 번 적용한 뒤 expense/event/participant 행 수와 ID를 비교한다. 업무 내용의 멱등성을 확인하되 last_seen_at 같은 감사 시각까지 불변이라고 가정하지 않는다.
6. **오류 월 보존**: BLOCKED 월에 기존 활성·비활성 내역을 모두 넣고 모든 컬럼 및 관련 일정·참석자 스냅샷이 유지되는지 비교한다. 다른 READY 월의 변경은 정상 반영되어야 한다.

## 원본 식별자 테스트

KAN-54의 UTF-8 JSON 배열 직렬화 → SHA-256 → 중복 순번 규칙을 구현할 때 아래를 검증한다.

- 원본 행 번호가 바뀌거나 중간에 다른 행이 삽입돼도 기존 내용의 키와 일정 ID 유지.
- `[일, 카드, 인원 원문, 구분]`의 앞뒤·연속 공백만 다른 두 입력은 같은 정규화 키.
- `카드=A|B, 인원=C`와 `카드=A, 인원=B|C`는 다른 키. 따옴표·역슬래시·줄바꿈도 직렬화 경계를 보존.
- 중복 내용은 서로 다른 순번을 받아 두 건으로 남고, 재업로드 시 같은 키 집합 유지.
- source_document_id는 ledger:YYYY-MM. 같은 원본 키라도 다른 달과 충돌하지 않음.
- 중복 순번이 0/1 중 어디서 시작하는지, 정규화된 일의 직렬화 표현은 구현 전에 명시한다. 현재 기호 #1/#2는 실제 포맷을 확정하지 않는다.

## 후속 작업 경계

KAN-58에서 동기화 서비스·엔티티 변경·일정/참석자 생명주기 테스트를 구현한다. GOOGLE_SYNC → CARD_IMPORT 전환은 기존 데이터 마이그레이션과 조회 권한·수정 금지·프론트 호환성도 함께 확인해야 한다. 이 준비 작업에서는 enum·DB·API를 변경하지 않는다.

KAN-59의 토큰·권한·HTTP 응답, KAN-60의 이력 조회까지 이번 자료가 통과시켰다고 간주하면 안 된다. 현재 확인은 JSON 문법·사례 ID 중복·예상 목록과 수치의 일관성뿐이며, 실제 DB 동작 테스트 통과를 뜻하지 않는다.
